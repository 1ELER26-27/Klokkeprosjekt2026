Fra idé til ferdig levert kode 🚀

En elevguide for samarbeid med GitHub og Git

I dette prosjektet bygger hele klassen klokken sammen! Hver elev implementerer sin egen funksjon, og alle endringer samles trygt i fellesprosjektet.

🛡️ Hvorfor denne rekkefølgen?

Sørger for at du aldri overskriver koden til andre, og at du aldri mister ditt eget arbeid.

⚡ Den gylne regelen:

Kod aldri direkte på main! Lag alltid din egen branch først.

💡
Bruk piltastene ➔ på tastaturet eller knappene under for å gå gjennom stegene.
Steg 1 av 10 Slide 2 / 12

🎯 Reserver oppgaven (Issue)

Før du rører en eneste kodelinje, må du si ifra hva du skal lage!

  • Gå til prosjektet på GitHub i nettleseren og klikk på fanen Issues.
  • Sjekk listen – se at ingen andre allerede har et åpent issue på din funksjon.
  • Trykk på den grønne knappen New issue og velg malen «Velg en funksjon».
  • Skriv inn funksjonsnavnet (f.eks. [FUNKSJON] fagFarge) og navnet ditt.
  • Trykk Submit new issue.
📌
Viktig huskeregel: Merk deg nummeret på issuet ditt (f.eks. #4). Dette nummeret skal du bruke når du leverer koden!
Steg 2 av 10 Slide 3 / 12

📥 Hent nyeste felleskode (Pull)

Kanskje noen andre i klassen fikk sin funksjon godkjent for ti minutter siden?

  • Åpne GitHub Desktop på PC-en din.
  • Sjekk at Current repository viser klokkeprosjektet.
  • Sjekk at Current branch står på main.
  • Trykk på Fetch origin øverst til høyre.
  • Hvis knappen endrer seg til Pull origin: Trykk på den for å laste ned de nyeste endringene til din PC.
✅
Nå er du garantert å starte med den ferskeste versjonen av prosjektet.
Steg 3 av 10 Slide 4 / 12

🌿 Lag din egen Branch (FØR du koder!)

En branch er ditt eget private sandkasse-område hvor du kan eksperimentere fritt.

  • I GitHub Desktop: Klikk på Current branch (der det står main).
  • Trykk på knappen New branch.
  • Gi branchen et beskrivende navn, f.eks: kari-fagFarge eller funksjon-fagFarge.
  • Sjekk at den lages basert på main, og trykk Create branch.
🛑
IKKE KOD PÅ MAIN: Hvis du begynner å skrive kode før du har laget branchen, blir det fort krøll. Lag alltid branchen først!
Steg 4 av 10 Slide 5 / 12

💻 Skriv koden i din funksjon

Nå åpner du Arduino IDE eller VS Code og koder løsningen din.

  • Åpne sketch/sketch.ino og finn funksjonen du reserverte.
  • Fyll inn navnet ditt: // Laget av: DittNavn.
  • Skriv logikken din inni funksjonen.
  • Spilleregler for god lagånd:
    • Endre kun inni din egen funksjon.
    • Ikke endre funksjonens navn, parametere eller returtype.
    • Ikke endre andres funksjoner, setup() eller loop().
💾
Husk å lagre filen med Ctrl + S jevnlig underveis!
Steg 5 av 10 Slide 6 / 12

📝 Fyll ut DOKUMENTASJON.md

God kode forklarer seg selv, men god dokumentasjon forklarer tankene bak!

  • Åpne filen DOKUMENTASJON.md.
  • Finn overskriften med navnet på din funksjon.
  • Fyll inn de 5 punktene:
    • Laget av: Navnet ditt
    • Hva gjør den? 1–3 setninger med egne ord
    • Parametere: Hva betyr verdiene som sendes inn?
    • Returverdi: Hva sender funksjonen tilbake?
    • Refleksjon: Hvorfor løste du det slik? Hva var vanskelig?
💡
Refleksjonen teller mye! Vis læreren at du forstår hvordan og hvorfor koden din virker.
Steg 6 av 10 Slide 7 / 12

🧪 Test koden lokalt

Lever aldri kode du ikke har prøvekjørt selv!

  • 1. Kompiler: Trykk Verify/Fluebein i Arduino IDE (Ctrl + R) eller Build i VS Code (Ctrl + Shift + B). Koden må bygge uten feilmeldinger!
  • 2. Test funksjonen:
    • I Wokwi-simulatoren i VS Code for å se LED-ring og Serial Monitor.
    • Eller last opp til en fysisk ESP32.
    • Eller legg inn en testlinje nederst i setup(), f.eks: Serial.println(fagNavn(MATTE));.
⚠️
Husk å rydde: Hvis du la inn en midlertidig testlinje i setup(), må du slette den før du leverer!
Steg 7 av 10 Slide 8 / 12

💾 Commit og Push til GitHub

Nå lagrer vi arbeidet og laster det opp til din branch på GitHub.

  • Gå tilbake til GitHub Desktop.
  • Sjekk Changes til venstre: Kun sketch.ino og DOKUMENTASJON.md skal være endret!
  • Nederst til venstre: Skriv en kort commit-melding: Implementert fagFarge() og oppdatert dokumentasjon
  • Trykk på den blå knappen Commit to <din-branch>.
  • Trykk på Publish branch (eller Push origin) øverst.
☁️
Nå ligger koden din trygt på GitHub i din egen branch!
Steg 8 av 10 Slide 9 / 12

🚀 Opprett en Pull Request (PR)

En Pull Request ber læreren om å godkjenne og merge koden din inn i fellesprosjektet.

  • I GitHub Desktop: Trykk på den blå knappen Create Pull Request (dette åpner GitHub i nettleseren).
  • Sjekk at toppen viser: base: main ← compare: din-branch.
  • Fyll ut malen i tekstfeltet (hvilken funksjon, testmetode, og sjekkliste med [x]).
  • Trykk på den grønne knappen Create pull request.
🎯
SUPER-VIKTIG: Ikke glem linjen Closes #<nummer>!

Helt nederst i PR-beskrivelsen skriver du f.eks. Closes #4 (erstatt 4 med ditt eget issue-nummer fra Steg 1 – husk: ingen mellomrom mellom # og tallet!).

✨ Hva skjer da? GitHub kobler PR-en til oppgaven din, og lukker issuet automatisk i samme sekund som læreren godkjenner og merger koden! Du slipper å lukke det manuelt.

Steg 9 av 10 Slide 10 / 12

⏳ Følg med på sjekken og tilbakemelding

GitHub tester koden din automatisk med én gang!

  • Vent 1–2 minutter: Se etter status nederst på PR-siden.
    • ✅ Grønn hake: Koden kompilerer fint! Alt er klart for lærer.
    • ❌ Rødt kryss: Koden har en skrivefeil eller byggefeil. Rett feilen på PC-en din, lagre og gjør en ny Commit + Push på samme branch!
  • Hvis læreren ber om endringer: Ikke lag ny PR! Bare gjør endringene lokalt og push på nytt på samme branch – da oppdateres PR-en av seg selv.
  • Når alt er godkjent: Læreren merger PR-en din! 🎉
Steg 10 av 10 Slide 11 / 12

🧹 Rydd opp til neste oppgave

Når PR-en din er merget, skal du gjøre klar PC-en for neste runde.

  • Åpne GitHub Desktop.
  • Bytt Current branch tilbake til main.
  • Trykk på Fetch origin og deretter Pull origin.
  • Nå har din lokale main fått med seg koden du nettopp leverte, flettet inn sammen med alle andres kode!
  • Klar for neste oppgave? Start på nytt fra Steg 1! 🚀
🏆
Gratulerer! Du jobber nå akkurat slik profesjonelle programvareutviklere jobber i team.
Huskeregel Slide 12 / 12

🌟 De 3 gylne reglene

1. Lag branch FØR du koder

Aldri rør koden mens du står på main. Alltid lag en ny branch først.

2. Husk dokumentasjon & issue

Fyll inn DOKUMENTASJON.md og husk å skrive Closes #nr i Pull Requesten din.

3. Rett opp på samme branch

Får du rødt kryss (❌) eller kommentarer fra lærer? Ikke start på nytt! Bare fiks koden på PC-en din, og gjør en ny Commit + Push på samme branch. Da oppdaterer GitHub alt automatisk.
